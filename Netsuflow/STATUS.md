# R&D status

Last updated: 2026-08-27

## Decision

HyperFrames is the first real renderer candidate. The product boundary is a
thin OpenFX Generator backed by an engine-neutral, out-of-process renderer
service. Remotion remains a planned second adapter, not discarded work.

This is a renderer-order decision, not a rewrite decision. The current native
plugin, protocol, session descriptor, fake renderer, and most cache logic are
shared foundations.

| The host can play a composition back at speed | **Yes, once the frames exist.** Nothing makes a browser screenshot into a 24 fps source — the editor's Live tab is smooth precisely because it captures nothing. | NetsuFlow is reachable from the application | **Yes, as of this slice.** `core/flow.js` supervises the renderer service as a spawned child, reads the ports off its announcement line, and proxies the editor API behind `flow:*` IPC channels, aligned across the handler table, the typed client and the mock. | Raw RGBA is the right thing to keep on disk | **No — that reasoning only ever ruled out PNG.** "A PNG decode costs as much as the capture it replaces" is true and says nothing about a codec built for speed. Storing raw cost 7.91 MiB per 1080p frame: **2373 MiB for a 300-frame composition**, measured on the real service. Node 22 ships zstd, so the store compresses now. | The cache setting is a quality setting | **No, and the panel says so.** All three tiers — fast (zstd 1), compact (zstd 9), raw — are lossless; a test writes incompressible pixels through each and asserts the bytes come back identical. ## Current implementation audit

Already reusable:

- `com.netsurush.netsuflow.generator` plugin identity;
- Generator render callback and byte/float host output handling;
- `binding`-based frame requests;
- versioned authenticated TCP protocol;
- session descriptor and reconnection;
- response validation, deadlines, diagnostic frames, and plugin last-frame cache;
- fake renderer and adversarial tests.

Required common correction before either real engine is production-ready:

- normalized props and their revision must participate in frame requests and
  every cache key. The Inspector currently fetches `Props JSON`, but the current
  native `FrameRequest` does not carry that value and its `FrameKey` does not
  invalidate on props changes. [S-NF-OPENFX] [S-NF-BRIDGE]
- frame-scoped Fusion control values and their canonical hash must also enter the
  request and every cache layer before animated controls are enabled.

## Go/no-go gates

1. **Host gate — conditional pass.** Loading, pixels, frame mapping, no tiling,
   clean teardown, and core bridge recovery are observed. Remaining manual
   scenarios stay listed in the T01/T03 reports.
2. **Common bridge gate — pass out of host; core path pass in host.** Keep the
   existing evidence and finish the remaining hostile in-host cases before a
   product claim.
3. **HyperFrames engine gate — started.** The dependency surface is frozen,
   fingerprinted, and guarded against drift; the licence position is measured
   rather than inferred. [S-NF-H01-DEPS] Still open: keeping one capture session
   alive, rendering random requested frames, decoding to straight RGBA8, and
   proving alpha, memory stability, and deterministic invalidation.
4. **Interaction gate — not started.** Measure cached and uncached scrubbing on
   representative HyperFrames compositions.
5. **Engine abstraction gate — not started.** Run the same conformance suite
   against the fake engine and HyperFrames; later add Remotion without changing
   the plugin protocol.
6. **Parameter gate — not started.** T10 proves constant controls, Fusion
   keyframes, stable slot assignments, value-at-time transmission, and exact
   invalidation without stale frames.
7. **Delivery gate — not started.** Package Node, Chromium, HyperFrames,
   notices, repair, update, and uninstall on Windows. macOS follows only after
   real hardware validation.

No product claim is promoted from unknown to confirmed without a dated report
and reproducible evidence.

## Deferred Studio track

The future custom NetsuFlow Studio editor is now specified separately under
[`studio/`](studio/README.md). It reuses HyperFrames SDK/Player and only those
Studio components that pass an embedding test, while NetsuRush owns the UI,
Resolve integration, persistence, and publishing. The current agent is not
accepted as the Studio agent; a change-set redesign has its own research and
test gate. No Studio implementation is considered started, and the OpenFX/
HyperFrames extension remains the active prerequisite.
