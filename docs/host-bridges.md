# Host bridges

Notes for the code that talks to other editing applications: the Adobe CEP panel and NetsuBridge (timeline transfer). **Neither is verified at runtime in CI** — both need the host applications installed.

## Adobe bridge (`adobe-cep/` + `core/adobe.js` + `src/components/adobe/`)

A dockable CEP panel for Premiere Pro and After Effects.

- **CEP, not UXP** (requirement: support hosts from 2020). UXP for Premiere only exists from 25.6, and UXP for After Effects does not exist at all. After Effects has no UXP path, so CEP + ExtendScript stays the only route there.
- **Engine ceiling**: CEP is frozen at **CEF 99** (CEP 12 is the last major release; 2020-era hosts are CEF 61–74) while Tailwind v4 needs Chrome 111+. Consequence measured: **`color-mix()` does not exist**, so every Tailwind opacity modifier (`bg-black/75`, `bg-primary/15`…) compiles to `color-mix(in oklab, …)` and renders **transparent** in the panel. `opacity-*` and `rgb(0 0 0 / .1)` are fine. Fix case by case with an explicit class.
- **The panel shell is its own HTML/CSS/JS**, zero build, conservative syntax (no `?.`/`??`, no flex `gap`, promises and `var`) because of CEF 61. `js/CSInterface.js` is a hand-written wrapper over the CEP runtime, every call guarded on `__adobe_cep__` so it no-ops when absent.
- **Remote view is the nominal mode**: the React app is loaded in an **iframe** inside the panel and auto-shown as soon as the core is online. The URL is resolved by probing Vite in dev, otherwise `http://127.0.0.1:8730/app/` where `core/appstatic.js` serves the built renderer (anti-traversal, SPA fallback; requires Vite `base:"./"` so assets are relative). The Win32 "embed by SetParent" flow was **removed everywhere — do not reintroduce it**.
- **The shell has no bar of its own** (its label duplicated the Adobe panel title): reload/close live in the remote header and travel back by `postMessage`. **The `ready` acknowledgement is mandatory**: without it at mount, a blank iframe (missing build, core stopped mid-load) would trap the user in an empty panel with no button — the shell's 20 s watchdog returns to the home screen instead.
- **File dialogs**: the remote app cannot open a Tauri dialog, so it posts a message to the panel, which opens the native CEP dialog and returns **real disk paths**.
- **Flow**: panel → `fetch` on `127.0.0.1:8730` (localhost, CORS already open) + `EventSource /events`; a 5 s heartbeat marks the panel connected. Scanning calls `evalScript` on a dispatcher that routes by `BridgeTalk.appName` to the per-host script, which returns JSON built by a hand-written ES3 stringifier, POSTed back to the core and broadcast to the renderer. The reverse direction is an SSE command channel.
- **`AdobeSnapshot` is in SECONDS** (host-agnostic, like the voice module's word timestamps): Premiere converts its **ticks** in the jsx (254,016,000,000 per second; exact fps = ticks ÷ timebase), After Effects is natively in seconds.
- **Frames are computed BY THE HOST, never derived from seconds** for timeline reading. Premiere converts ticks (integers, exact multiples of a frame) using the **source** frame rate, which is not the sequence rate. **After Effects is the hard case**: it trims in **comp** time, so `inPoint − startTime` is wrong as soon as a layer is retimed — undo the stretch (`× 100/stretch`) and go through `timeRemap.valueAtTime()` when remapping is active (there is no linear relation otherwise), then reorder the bounds for a reversed layer (negative stretch). Self-inflicted trap: our own AE build writes `stretch = scale × 100` when fitting, so reading back a comp we produced returned double.
- **Nesting has to be resolved on both hosts.** In AE a layer whose source is a comp has no file: walk down to the footage (depth capped at 4, each level's source time being the next level's internal time) — otherwise the shot came out with `path:null` and **disappeared** from the grid. In Premiere a nested **sequence** returns an empty media path, with the same result; walk down the same way (match the sequence by node id, take the visible clip on the **top** track, carry the bounds level by level). A `direct` flag marks the nominal, non-nested case: only that one keeps tick exactness, since the descent carries bounds in seconds. Source bounds are **inclusive** (Adobe's `outPoint` is exclusive → `-1` on the way back), the same convention as Resolve. Limitation: if a nested item itself contains a montage, only the shot covering `srcIn` is reported.
- **Premiere sources: use a project index, never `findItemsMatchingMediaPath` alone.** On a real project that API returns an **empty** list even though the rush is there (case, separators, sources in sub-bins), and the build failed with "clip not found or import failed". Try the API, fall back to an **index of the project** (same walk as the snapshot, key = path normalised to forward slashes and lowercase), and import only as a last resort — invalidating the index afterwards.
- **Never pass a file that is missing from disk to the importer**: Premiere then opens a **modal** dialog that `suppressUI` does not cover, which freezes ExtendScript — the panel goes silent until the job's 120 s timeout (~20 minutes of silence observed). Check the disk first and return a distinct `MEDIA_MISSING` error. Same guard on the AE side.
- **ExtendScript is ES3: a reserved word used as a property name makes the WHOLE file unparseable** (`{ in: … }` → `SyntaxError: Illegal use of reserved word 'in'`). Adobe then keeps the **last version that loaded** in memory: the corrected file on disk has **no effect** in the host, and the visible symptom is `NR_* is not a function` or, worse, silently empty reads — never an error pointing at the syntax. Observed for real: one `ticks.in` froze a host script on a stale version for several sessions while every fix went nowhere. Quote the key (`"in":`) and access it as `obj["in"]`. **`test/adobe-jsx-es3.test.cjs` locks this**, covering ES3 reserved words as keys or dotted accesses plus post-ES3 constructs (`=>`, template literals, `const`/`let`, `JSON.parse`, ES5 methods), because Node accepts all of it and nothing else in the repo would catch it.
- **The panel reloads the jsx files when their disk fingerprint changes** (mtime + size); otherwise an app update would keep the scripts loaded at panel open until the host restarts. The **dispatcher file is part of that set** even though it is the manifest's `ScriptPath`: Adobe only loads it when the **application** starts, so omitting it left a stale dispatcher next to fresh siblings — observed as a `not a function` that only a Premiere restart fixed. Three guards, each fixing a real case: an **unreadable** fingerprint returns an always-new value (a constant marker meant the stamp never changed again, so no reload for the panel's whole life); each file is evaluated **separately** with its own error, so the first failure does not swallow the others; and a host reply containing "is not a function" forces a reload and **one** job replay, with the dispatchers checking `typeof` before calling so they return a typed staleness error rather than an opaque `ReferenceError`.
- **Installation and updates** (`core/adobePanel.js`, tested): the extension is a **copy** in `%APPDATA%\Adobe\CEP\extensions`, so nothing updates it when the app evolves. The setup screen offers to install it when a host is detected, and the core **re-syncs it at startup** as soon as the installed copy differs from the shipped one. Comparison is by **content hash**, not mtime: `copyFileSync` does not preserve dates, so an mtime comparison would reinstall on every start, and a content hash also detects an extension installed by the standalone script (therefore with no state). The panel also **installs itself** when none is present and a host executable exists on the machine: the extension is inert until a host loads it, so placing it costs nothing, while waiting leaves the bridge silent until the user finds the button. The **policy lives in a pure, tested function**, not in the effect code, and honours two refusals: automatic management turned off, and a panel **removed by hand** (install recorded but nothing on disk any more) — reinstalling it on every start would amount to refusing the uninstall. A host **open** during the update keeps the old copy loaded (CEP reads the extension at app start), so the result lists the apps to restart, cleared once they are closed.
- **Manifest ranges must stay OPEN** (`[0.0,99.9]`) with `RequiredRuntime CSXS 7.0`, and `PlayerDebugMode` must be set for CSXS 9→15. Otherwise Adobe **silently rejects** the unsigned extension: it is simply absent from the Extensions menu while every other panel loads.
- **`$.fileName` is empty under CEP**, so the dispatcher cannot `evalFile` its siblings and the JSON helper ends up undefined ("snapshot failed"). The **panel** loads the jsx files from `cs.getExtensionPath()+"/jsx"` before any scan or job.
- **A Diagnostic button** in the Adobe tab reports the folder, the manifest on disk, the real `PlayerDebugMode` registry value and the CEP log lines — debugging without PowerShell.
- **Write path is a job round-trip through the panel**: renderer → core (job registry, 120 s timeout, 10 min for a full timeline placement) → SSE command → panel `evalScript` → host script → POST result → promise resolved. The payload is **embedded as a literal in the evaluated code**, since ES3 has no `JSON.parse`.
- **Premiere frame-math limitation (assumed)**: `createNewSequence` exposes **no** frame rate and no API changes it afterwards, so the Resolve invariant "set `timelineFrameRate` before creating" has **no equivalent** — sequence rate is a runtime risk. Source trimming stays frame-accurate.
- **An AUDIO medium has no frame rate, and Premiere invents one**: `getFootageInterpretation().frameRate` returns an absurd value on an audio-only item (**2.754e-8** measured on a `.wav`). Propagated, it collapsed source bounds to `0/0`, i.e. a one-frame clip that `AppendToTimeline` refuses — that was the whole "audio does not transfer" bug, and neither keyframes nor fades had anything to do with it. Two guards: accept a rate only within `[1, 1000]`, and give an audio clip **the sequence rate** (which the Resolve reader already does).
- **Premiere audio level is a 0..1 float OFFSET BY 15 dB**, never decibels: `dB = 20·log₁₀(v) + 15`, so 0 dB is ≈ 0.178, not 1 (the fader goes to +15 dB). Measured: a fade down to −18.3 dB returned `0.0216`, which was passed straight through as gain. Silence maps to −96 dB rather than −∞, which no exchange format carries. Report comparisons stay in **normalised** level on both sides; converting only one compares different quantities and reports a discrepancy where the placement is exact.
- **Premiere motion values are FRACTIONS, not pixels**: `Motion.Position.getValue()` returns `[x, y]` normalised (0 = left/top edge, 1 = right/bottom), and `Anchor Point` does the same over the **source** size. Reading them as pixels turned a centred clip (0.5, 0.5) into a (−959.5, −539.5) offset — the observed symptom was "the transforms are excessive", never "the units are wrong". One conversion function per direction, exercised by `test/transfer-ppro-units.test.cjs` **in a `vm`**, because a regex over the source would not prove the maths. `Scale` and `Opacity` **are** percentages and rotation is in degrees: do not normalise those.
- **Sub-nav in the CEP panel**: the app's sub-navigation lives in the **title bar**, which the panel does not have, so the remote view renders it in a dedicated horizontally scrolling strip — without it, whole sub-pages were unreachable inside the host.
- **Responsive narrow panel**: the cut studio measures its **real width** and switches to a single column below 640 px, bounding the player so the grid keeps a minimum width. Before that, a fixed 360 px player left ~14 px for the grid in the CEP panel and the toolbar stacked on itself, which reads as "the icons disappeared". Model and precision pickers are **not hidden** in remote mode (they were unfindable), just narrowed.
- **A signed `.zxp`** can be produced for distribution without `PlayerDebugMode`; the dev script installs unsigned plus the debug flag.
- **Host support horizon**: CEP loads from Premiere Pro 2020 (14.0) / After Effects 2020 (17.0) up to the 2026 releases, but **CEP 12 is the last major version** (security fixes only) and **Premiere Pro's ExtendScript support ends in September 2026**. Concretely: calls that go through the undocumented **QE DOM** are already stubbed on some builds, while the **public** APIs hold across the whole range. Any feature built on the QE DOM must therefore ship its host-less fallback.

## NetsuBridge (`src/components/transfer/` + `core/transfer/`)

Copies a timeline from one editing application to another. **Research journal: `docs/timeline-transfer-research.md` — read it before reopening this topic**: several apparently obvious routes were already tried and are expensive, including one that crashes Resolve.

**Supported pairs, exhaustively**: Resolve → Premiere Pro · Resolve → After Effects · Premiere Pro → Resolve. Premiere and After Effects already talk to each other natively (Dynamic Link), so a transfer between those two adds nothing; After Effects is therefore only ever a **destination**. The pair table exists on both sides and the core enforces it.

- **Neutral exchange document** (`core/transfer/doc.js`): one reader and one writer per host, not one bridge per pair — six pairs collapse into three reads and three writes. `TransferClip` = `{kind, track, path, name, fps (SOURCE), srcFrames, srcIn/srcOut (INCLUSIVE frames), tlStart/tlEnd (timeline frames, end EXCLUSIVE)}`. The whole module is **pure** (no I/O), so it is testable without any host installed.
- `normalizeDoc` rebases positions onto 0 (a Resolve timeline commonly starts at 01:00:00:00), clamps bounds to the source length, sorts, and **deduplicates LINKED audio**: on a Premiere sequence the sound of an A/V rush occupies A1 with the same file and range as the picture on V1, so placing it again would double it.
- **Writing uses ABSOLUTE positions** — that is the difference from the "append shots" builders, which lay clips end to end on one track (right for a selection of cuts, wrong for a montage whose gaps and stacking are part of the information). Resolve: `AppendToTimeline` with `recordFrame` + `trackIndex` + `mediaType` (1 = video only, 2 = audio only, so linked audio is not duplicated). Adobe: `overwriteClip` at ticks — **never `insertClip`**, which would ripple the montage — and AE layers added in **increasing** track order because `layers.add()` inserts at the top.
- **`AppendToTimeline` returns `[]` when it refuses — and `[]` is truthy in JS.** Testing the raw return counted every refusal as a success, so a clip vanished without any counter moving. A refusal is retried by relaxing `trackIndex` first, then `mediaType`, and the relaxation is reported. In "append" mode the document is placed **after** existing content rather than at its absolute position, which would overwrite it.
- **A TimelineItem is found again by `GetUniqueId()`, never by object identity.** The Python bridge builds a **new** proxy object on every decode, so comparing the object returned by `AppendToTimeline` with the ones read back never matched, and the fallback fingerprint failed as soon as the source start frame came back anchored to the start timecode. Measured result: 5 clips placed, **0 properties applied** — no zoom, no rotation, no opacity.
- **Tracks**: Resolve has `AddTrack`; Premiere has no public one, so go through the QE DOM (guarded, result verified against the real track count) and **clamp to the last track while saying so**, rather than losing the clip.
- **Media handling** (`core/transfer/prepare.js`): `copy` (link the original files, default) · `remux` (lossless re-container, when the target host cannot read the source container) · `reencode` (editing codec, frame-exact cut). The heavy lifting reuses the AE media preparation, then bounds are **re-based into the produced files** (the file-relative in-frame becomes the new source in, and the original length no longer applies). An output folder is mandatory as soon as a file is written.
- **Encoding settings are the EXPORT PROFILE settings**, not a second vocabulary: the tab renders the same rows as the profile editor through a shared hook, and labels come from the export namespace — translating them twice would let them diverge. On the core side the media preparer receives an **injected** format, so the AE vocabulary stays the default while NetsuBridge passes one built from the shared encoding arguments. Hardware encoder selection is the same code as file export.
- **The codec catalog is RESTRICTED to editing** (`transferEncoding.ts`, tested): every file produced here goes back into an NLE, so a codec the target cannot open is not a choice but a failed transfer. Excluded: **AV1 / VP9 / FFV1** (delivery and archival, never editing), **MKV and WebM** (neither Premiere nor After Effects imports Matroska), **H.264 Baseline / 10-bit / 4:2:2 / 4:4:4 and H.265 12-bit / 4:4:4** (outside NLE decoding; above 8-bit the universally open route is H.265 Main 10), **Opus** (never muxed in MOV), **MP3** (encoder delay), **FLAC and ALAC** (not imported by Premiere). The restriction applies **only** in this tab; the full catalog serves delivery.
- **A preview before placing** (`transfer:read` → document summary: clips read, V/A tracks, duration, missing sources). Without it, a failed transfer did not say whether reading or writing was at fault.
- Panel jobs get a **10-minute** timeout, since a full montage exceeds the standard 2 minutes.

### Animations — the asymmetry is entirely on the Resolve side

Verified against the API shipped with Resolve: `TimelineItem.SetProperty` sets **fixed** values, **no keyframe method exists**, and **no gain, pan or mute command is exposed** — so an audio fade coming from Premiere has **no entry point at all**; that is not a reading defect. On the Adobe side ExtendScript reads **and** writes everything. Hence the rules below.

- **Animation is ALWAYS read from the host's XML export, never from its API — on both sides.** The pattern is identical in both directions: the API or snapshot carries the **structure** (paths, tick-exact bounds, tracks, flattening of nested sequences), the export carries the **keyframes**, and a merge step grafts the second onto the first. On the Premiere side the export call needs `suppressUI = 1`: without it a modal warning freezes ExtendScript and the job times out. Premiere's `ComponentParam` *can* return keyframes and we still read it, but **a scan can return correct bounds and an empty component collection**: measured in production, seven clips out of seven with not a single property while the transforms were clearly there. Nothing distinguishes "no animation" from "not read", hence a diagnostic dump plus the XML, which is an **independent** source. One parser, one graft, two hosts.
- A Premiere export also embeds **nested** sequences, so the parser targets the sequence **by name**; taking the first one would import another montage's animation.
- **Reading a Resolve timeline's animation means `Timeline.Export(…, EXPORT_FCP_7_XML)`** — there is no other output that carries it. The XML **never builds a timeline**: the parser is read-only and the merge only grafts keyframes onto the document read through the API, so source bounds, nested flattening and start-timecode rebasing stay the API's. Matching is per track, in chronological order, and **a track whose two readings do not hold the same number of clips is not matched at all** (guessing the alignment would put one clip's animation on another). Reading the export constant requires an attribute read on the proxy: it only forwards calls, so a constant would be invoked.
- **Writing an animation into Resolve means a Fusion composition** (`ImportFusionComp` is the API's only animation write). **`ExportFusionComp` returns the composition in standalone Fusion form**: page nodes come out as `Loader`/`Saver`, never `MediaIn`/`MediaOut`. Looking only for the latter made **every** skeleton unreadable, so no keyframe was ever placed and nothing pointed at the cause — accept both pairs. The composition is never written from scratch: start from the skeleton Resolve just exported, insert between its input and output, then **read it back** to verify the graft survived. A failure falls back to a fixed value and says so. Fusion space is normalised 0..1, origin **bottom** left, rotation counter-clockwise — the inverse of the document on all three counts.
- **A Fusion composition carries the clip's WHOLE framing, not just its curves**: the transform tool also writes the **fixed** position, anchor, scale, rotation and mirrors. Since the edit page's own resize applies **after** Fusion, rewriting those values with `SetProperty` **stacks** them: a clip arrived "too zoomed" carrying settings the user never set. When a composition is placed, every video property is therefore reported as carried by it and **no longer written**. Two corollaries, measured: opacity is rendered by a brightness/contrast node's alpha input, **never by a merge over a solid background** — the background imposes its size on the composition's output and short-circuits Resolve's automatic fit, which made any rush of a different resolution overflow; and an opacity of 100% places **no node at all**. The working composition is **deleted only if the import created another one** (comparing the count before and after): depending on the version, `ImportFusionComp` replaces the current composition's content instead of adding one, so "cleaning up" erased the animation just placed — which showed as animation appearing only on clips that already had their own composition.
- **An animated property must NEVER also be written with `SetProperty`** (the edit page's scaling applies after Fusion; the two would stack).
- **A source bound that cannot be read is NEVER copied from the other one.** Measured (Premiere 26 → Resolve 21): two `.wav` clips came out of the panel with unusable in/out points, the fallback copied the in onto the out, and Resolve silently refused the resulting one-frame clip — that was "the audio does not transfer at all", even though the files were correctly imported into the Media Pool. Two guards: the host script tries the track item's points, then the project item's, then the clip **duration**; and the document derives a missing bound from **timeline occupancy**, each deduction only ever working in one direction. Bounds are finally clamped to the length Resolve knows (`GetClipProperty('Frames')`), the only one of the two applications that exposes it.
- **ONE element without media makes `ImportTimelineFromFile` fail SILENTLY.** Measured on Resolve Studio 21.0.3 by bisecting the real file: a Premiere title is **synthetic** media whose `<file>` carries no `pathurl`, and its mere presence makes the call return `None` — no exception, no message, no log — whatever the options, declared version, DOCTYPE or path. The same file imports **perfectly** through File ▸ Import ▸ Timeline, because the UI can open a dialog for missing media where a script call cannot. That was the cause of sixteen consecutive refusals, and nothing in the document header was to blame. `core/transfer/xmeml/graphics.js` therefore translates those elements **before** the import (title → text generator, everything else dropped); without it, a single title condemns the whole transfer, keyframes included.
- **Second defect of the same direction, also measured**: Premiere writes `explodedTracks="true"` and emits each **stereo** file as **two mono clip items**, one per channel, on two tracks — it displays one, the importer places two, hence sound duplicated across two tracks. The audio-channel fixer keeps only the lowest-ranked channel and removes the track that held nothing else (otherwise every stereo file leaves an empty track). Grouping requires **everything** to match (file, position, bounds) and the ranks to **differ**: two clips at the same rank are sound deliberately placed twice.
- **Toward Resolve, the primary route is its own importer, not clip-by-clip placement.** `MediaPool.ImportTimelineFromFile(path, {timelineName, importSourceClips, sourceClipsPath})` applies what no script API can write: position/scale/rotation/opacity **with keyframes**, audio levels in dB **and** their automation, speed, titles, nested sequences. Rebuilding that by hand on top of `AppendToTimeline` reproduces native work less faithfully — and for audio it was outright impossible. So: the panel makes Premiere export its FCP7 XML, and the core hands it to Resolve. **API placement stays indispensable** where the importer cannot go: appending to an **existing** timeline (the importer always creates a new one), targeting a named timeline, or placing media the app just produced. Hence a capability check and an automatic, logged fallback. The result carries which vehicle was used and the UI says so, because the two do not deliver the same thing.
- **Two corollaries of the same measurement**: the return value does **not** prove anything (`None` can accompany a successful import — hence listing timelines before and after, without which you chain attempts believing they failed while each one adds a timeline to the project); and a sequence named "1" is refused when the call is made **without** options but passes as soon as a timeline name is given. The exchange file **survives** a refusal under a stable name and its path is surfaced to the UI, so the manual route stays a recovery that script placement cannot match, since the API writes no audio levels.
- **Titles are RECREATED on the target, not transferred as clips.** A title has no file and no source bounds: leaving it among the clips made every writer read it as a media reference, while filing it as "no media" condemned content that is perfectly transportable. It therefore lives in its own list on the document, next to what **nothing** can carry (colour mattes, adjustment layers).
  - Reading on the Premiere side: **the modern graphics accessor returns NOTHING on a NATIVE title** (measured: "absent" while the text effect was clearly in the component collection) — it only covers templates coming from After Effects. Look for the text component in the **collection** as well, and note that a title's motion lives in the graphics group, not in the standard motion group. The source-text parameter's value is a **JSON string**, read **by pattern and never with `eval`**, which would execute content from a third-party project (ExtendScript has no `JSON.parse`).
  - **A native title's text cannot be read through the API but can be read in the XML**: the parameter returns an opaque value (measured: a single glyph for a whole sentence), whereas the same parameter travels base64-encoded in the FCP7 export, where text **and** font are length-prefixed plain strings. The effect name tells you which string is the text (Premiere names a graphic after its content), and shape disambiguates when the user renamed it.
  - **Writing to Resolve: the title becomes an FCP7 text generator placed BY THE IMPORTER**, never inserted afterwards. Verified by round-trip: Resolve re-exports the string, font name and size verbatim, and places the title on the exact frame, track and duration. **`InsertFusionTitleIntoTimeline` is a RIPPLE, not a placement** — measured: inserting a title at frame 5 of a five-clip timeline **cut** the clip under the playhead and shifted three video and six audio tracks by the title's duration; locking lower tracks only makes the insertion fail. That path therefore survives **only for an empty timeline** and refuses, explicitly, as soon as the timeline holds anything.
  - Size is emitted **only when known** (imposing an arbitrary value would give a title at a size nobody chose). Converting a size from source pixels to a fraction of frame height and splitting a PostScript name into family + style are two accepted approximations, so the text axis is reported as **approximated, never exact**, even when everything places.
  - **Toward Resolve the font and size DO NOT survive — five routes measured, five dead ends**, not to be re-explored: (1) `fontsize` in the FCP7 generator is read, stored and re-exported but **never applied** to the render (two very different values give the same image); (2) an imported title is opaque — its Fusion composition count is 0, property reads return `null`, adding a composition returns `null` and exporting one yields an empty file; (3) a Text+ cannot be described in FCP7 (Resolve exports its own as an empty clip item without the text); (4) `SetProperty('ZoomX')` on an imported title does not resize it and **crashes Resolve**; (5) the native `.drt` format carries only the title **type**, not the styled text, size or font. The size **is** read correctly on the Premiere side (font size × layer scale, because enlarging a title by dragging its box changes the layer scale, not the size) and is written into the document; it is the importer that ignores it. The report logs both values so the user can copy them, instead of getting a default to diagnose.
- **Anchor point — the document's canonical convention is SOURCE pixels, origin top-left, Y downward** (Premiere's and After Effects'). Resolve counts it as an offset **from the centre** with Y upward, so the conversion needs the source dimensions (read from the clip resolution property on one side and from the metadata column on the other). **Without known dimensions the anchor is not written** rather than moved at random.
- **AE delivery through the panel**: the AE exporter already writes its `.jsx` to disk, so the panel runs it with `$.evalFile` inside the **open** After Effects. Launching `AfterFX.exe -r` assumed AE was already running with a ready project, otherwise the script fired before the project existed and the import was lost. Fallback is a logged launch, never silent.
